# Kiln Controller web app

A static page that talks to the controller over USB using the browser's **Web Serial** API. There's no build step and no server-side code: the files in this folder are the whole app.

- **Browsers:** Chrome, Edge, Opera, Brave or Arc on a desktop OS. Firefox and Safari have no Web Serial.
- **Secure context:** Web Serial only works on `https://`, `http://localhost` and local `file://` pages.
- **Demo:** open the page with `?demo` to run against an in-browser simulated kiln (30× speed; `?demo=120` for 120×) with no hardware.

## Run locally

**From disk:** double-click `kiln-controller.html` (or `index.html`, which forwards to it). It is a single self-contained file, so it can also be copied anywhere on its own.

Browsers won't load JavaScript modules from `file://` pages, so `index.html` and its separate `.js` files only work over http. `kiln-controller.html` is the same app with everything inlined, generated by:

```bash
python scripts/build_web.py
```

Rerun it after changing any file in `web/`.

**Over http:**

```bash
python -m http.server 8000 --bind 127.0.0.1 --directory web
```

Then open http://localhost:8000 (or http://localhost:8000/?demo).

The browser remembers the serial-port permission separately for `file://` pages and for `http://localhost`, so pick the port once in each.

Close any serial monitor or PlatformIO upload first; only one program can have the port open.

The first time, click **Connect** and pick the controller. After that, the page reconnects by itself on load and whenever the Dial is plugged back in, because the browser remembers the permission.

## Firing program editor

The **Firing program** card builds a ramp/hold program from control points: a time from the program start and the temperature to reach by then. The setpoint ramps linearly between points; two points at the same temperature make a hold. The chart labels each segment with its rate (°C/min) and length (minutes), and the table shows the same numbers.

Editing on the chart:

- **Drag** a point to change its time and temperature. It snaps to 5 min / 5 °C; hold **Shift** for 1 min / 1 °C. A point can't be dragged past its neighbours, and the first point stays at 0:00.
- **Click** empty space to add a point there.
- **Double-click** a point to delete it.

The editor's program is saved in the browser's local storage, and can be exported or imported as JSON:

```json
{"format":"kiln-program","version":1,"name":"Example bisque","wait":true,"points":[{"min":0,"c":20},{"min":180,"c":200}]}
```

**Send to controller and start now** stores the program in the controller's flash (one program slot) and starts it. From then on the controller runs it by itself:

- **Waiting for the kiln** (the **Wait for the kiln if it falls behind** checkbox, on by default and stored with the program): the program clock pauses whenever the kiln is more than 15 °C *behind* the profile (too cold on a rise or hold, too hot on a cooling segment), so a slow kiln still gets the full ramp and hold times ("guaranteed soak"). With it off, the setpoint follows the clock alone, even if the kiln can't keep up.
- **Always from the start:** a program always starts at 0:00, even if the kiln is still warm. A warm kiln on a rising profile simply runs ahead until the profile catches up.
- **Locked while running:** the Dial's knob is locked, a click shows "HOLD TO STOP", and a long press stops the program. The page can stop it too.
- **Checkpoints and resume:** progress is saved every minute. After a reboot, the program resumes if the kiln is still within 50 °C of where the program was; otherwise it is abandoned and the Dial says so.
- **Finishing:** at the end the heat turns off and the Dial beeps.

The card shows whether the controller's stored program matches the editor, and **Load from controller** copies it back into the editor. While a program runs, the live card shows its progress.

### Changing a program while it runs

While a program runs, a dotted blue **now** line on the program chart shows its position, with a dot at the kiln's actual temperature. You can:

- **Edit any point**, before or after "now". **Send to controller and start now** swaps the edited program in without stopping. The controller keeps its own current time, so the few seconds a send takes don't matter.
- **Move to a different time:** hover over the now line (the cursor becomes a left-right arrow) and drag it forward or backward. It snaps to whole minutes; hold **Shift** for seconds. A solid "start at h:mm" marker stays where you drop it while the dotted line keeps tracking the live position. Sending then continues the program from the marker's time, edits included. Press **Esc**, or drop the marker back on the dotted line, to cancel.

The setpoint may step suddenly when you do either. That's intended: the kiln tolerates step changes. With **Wait for the kiln** on, jumping to a much hotter point pauses the program clock until the kiln catches up, as it would for any lag.

If the editor holds a different program from the one running, sending replaces it, and the confirmation says so.

## PID tuning

Kilns respond differently hot and cold: radiation makes losses far larger at high temperature. The controller keeps a small **tuning table** of up to 4 points. Each point holds P, I and D gains plus the **holding power**: the power needed to stay at that temperature.

- **Gain scheduling:** gains are interpolated linearly between points, keyed on the setpoint (not the measured temperature, so measurement noise can't make the gains jump). Below the first point and above the last, the end values apply.
- **Feed-forward:** the holding power is interpolated the same way, falls to 0 at ambient below the first point, and is extended above the last. It is added as a baseline, so the PID only corrects around it. This is what makes I uncritical and removes droop at high temperature.
- **No points** means the **baseline gains** at every temperature and no feed-forward. The baseline gains are also what a step test uses to heat up and hold before any points exist. They're editable on the card (stored on the controller with the table); **Built-in defaults** restores P 3.3 %/°C, I time 60 s, D time 8 s, which are what the rule below gives for a Paragon QuickFire measured at 150 °C (about 2 °C/s at full power, 10 s dead time). **Use as baseline gains** on a step-test result copies its suggested gains there.

**Step test.** It runs on the controller, so it doesn't need the computer:
1. Heat to the test temperature and hold it until steady: within ±5 °C, and drifting less than 5 °C, for 5 minutes. The average power over that window, corrected for any drift (using the heating rate measured in step 3), is the holding power. (The firmware can also ramp the heat-up setpoint, `StepTestConfig::approach_c_per_min`; it is off by default.)
2. Add a fixed power step (20 % by default) with the control loop off, and record the rise. If the holding power is so high that there isn't 5 % of room above it (very hot tests), the power is stepped *down* instead and the cooling response is recorded; the maths is the same.
3. Stop once the heating (or cooling) rate has peaked (no sooner than 5 minutes in), or after ±50 °C or 60 minutes. Heating then stops.

While it runs, the card shows which of the three steps it's on, a progress bar, what it's waiting for (e.g. "steady for 3:10 of 5:00, moved 0.4 of 5 °C allowed"), an estimate of the time left, and what happens next. The Dial shows the same progress on its bottom line. A small kiln usually finishes in 15–30 minutes.

From the response it measures the heating rate per unit of power and the dead time (tangent method), and suggests gains with the SIMC rule for a lag-dominant process, tuned fast (closed-loop time constant = half the dead time, close to critically damped): **P** = 1 / (rate × 1.5 × dead), **I** time = 6 × dead, **D** time = dead / 2, with the dead time taken as at least 10 s. The small D damps overshoot from the elements' heat capacity. You can set D to 0 for hot points.

Gains are shown as % power per °C of error (P), per °C·min (I), and per °C/min of change (D). The card's chart shows how P, D and holding power vary across the temperature range.

Typical setup: run a step test at about 150 °C and another at about 750 °C, add both results to the table, and send it. Because holding power rises faster than linearly at high temperature, a third point around 1000–1100 °C helps if you fire hotter than about 1000 °C.

## What stops heating

Besides Stop (on the page, or a long press on the Dial) and a program or step test finishing, only these stop the kiln. Whenever one does, the page shows why in a banner that stays until you dismiss it, even after reconnecting, and the Dial shows it in red until you click. The CSV export notes it in the `event` column.

| Reason | When |
|---|---|
| **No temperature reading** | No usable thermocouple reading for **30 s** while heating. During a shorter dropout the controller holds the last power level, and the program clock and step test pause. |
| **Over temperature** | The kiln reads 1425 °C or more. |
| **Step test failed** | It took more than 6 hours, the kiln didn't respond to the power step, or the holding power left less than 5 % of room in either direction. |

**Thermocouple warnings.** In a hot kiln, the elements leak current through the hot refractory into the thermocouple, mostly while the SSR is on. The MAX31855 flags that as "short to GND" or "short to VCC", but its temperature reading is still good. The controller uses those readings (if within 50 °C of the current temperature; the median filter rejects any remaining spikes), counts them, and the page shows a yellow note with the count. They never stop heating. An open thermocouple or a missing board gives no reading at all, so those count towards the 30 s limit.

A fault present when you press Start (no sensor, open thermocouple) still prevents heating from starting.

## Protocol (v1)

Newline-delimited JSON over USB CDC. The baud rate is ignored, but **never open the port at 1200 baud**: the firmware treats that as "reboot into the bootloader" (it ignores it while heating).

The device pushes a status line once a second. If the computer keeps the port open but stops reading, the device drops output rather than blocking:

```json
{"evt":"status","ms":12340,"state":"run","sim":false,"pv":842.50,"sp":850,"duty":0.620,"ssr":1,"fault":"","raw":838.25,"cj":24.125,"frame":"346C1820"}
```

| Field | Meaning |
|---|---|
| `state` | `"off"`, `"run"` (setpoint mode), `"program"` or `"tune"` (step test) |
| `pv` | actual temperature in °C, or `null` when the sensor is faulted |
| `sp` | active setpoint in °C (the program's current value while one runs) |
| `duty` | controller output, 0–1 |
| `ssr` | heater output right now, 0 or 1 |
| `fault` | `""`, or e.g. `"TC OPEN"`, `"NO SENSOR"`, `"OVER TEMP"`: no usable reading right now (or over temperature). While heating, a sensor fault stops it only after 30 s |
| `sim` | `true` on the `m5dial-sim` firmware build |
| `warn` | only after flagged-but-used readings since heating started: `{"what":"TC SHORT GND","n":12}` |
| `stopped` | only while off, until heating starts again: why it last stopped, `{"reason":"NO TEMP READING","detail":"...","alarm":true,"ago":42}`. `reason` is one of `STOPPED BY PC`, `STOPPED ON DIAL`, `PROGRAM DONE`, `STEP TEST DONE`, `STEP TEST FAILED`, `NO TEMP READING`, `OVER TEMP`; `alarm` is true for the last three |
| `tune` | only during a step test: `{"phase":"heating"\|"settling"\|"stepping","temp","el","phase_el"}` (seconds). While settling it adds `steady` (seconds the current steady window has lasted), `need`, `band`, `drift` (°C moved since the window began) and `max_drift`; while stepping, `rise` (°C since the step), `max_rise` and `max_s` |
| `prog` | only while a program runs: `{"name","el","total","seg","segs","wait"}`. `el` and `total` are seconds of program time; `wait` is true while the clock is paused for the kiln |

Requests carry an `id`, which the reply echoes:

| Request | Reply |
|---|---|
| `{"id":1,"cmd":"hello"}` | `{"id":1,"ok":true,"fw":"0.8.0","proto":1,"sim":false,"sp_min":0,"sp_max":1400,"max_points":32,"max_tune_points":4}` |
| `{"id":2,"cmd":"setpoint","value":850}` | `{"id":2,"ok":true}` |
| `{"id":3,"cmd":"start"}` | `{"id":3,"ok":true}` (setpoint mode), or `ok:false` with the fault name |
| `{"id":4,"cmd":"stop"}` | `{"id":4,"ok":true}`; stops either mode |
| `{"id":5,"cmd":"program.put","name":"Bisque","wait":true,"points":[[0,20],[180,200],[240,200]]}` | `{"id":5,"ok":true}`. Points are `[minutes, °C]`, with minutes as a decimal (seconds are kept); the first must be at 0, times must increase, 2–32 points. `wait` (default `true`) pauses the program clock while the kiln is more than 15 °C behind the profile |
| `{"id":6,"cmd":"program.get"}` | `{"id":6,"ok":true,"program":{"name":"Bisque","wait":true,"points":[[0,20],...]}}`, or `"program":null` |
| `{"id":7,"cmd":"program.start"}` | `{"id":7,"ok":true}`, or `ok:false` (`"no program stored"`, `"program already running"`, a fault name) |
| `{"id":9,"cmd":"tune.start","temp":150,"step":0.2}` | Start a step test (50–1300 °C, step 0.05–0.5). Refused while a program runs |
| `{"id":10,"cmd":"tune.result"}` | `{"id":10,"ok":true,"result":{"temp","hold","step","rate","dead","kp","ki","kd"}}` for the last completed test, or `"result":null` |
| `{"id":11,"cmd":"tuning.get"}` | `{"id":11,"ok":true,"base":{"kp","ki","kd"},"default_base":{...},"points":[{"temp":150,"kp":0.039,"ki":0.00012,"kd":0.77,"hold":0.023},...]}`. `base` is the baseline gains, `default_base` the built-in ones |
| `{"id":12,"cmd":"tuning.set","points":[...],"base":{...}}` | Store the tuning table (0–4 points, any order) and, if given, the baseline gains (otherwise they're kept). Raw units: `kp` duty/°C, `ki` duty/(°C·s), `kd` duty/(°C/s), `hold` 0–1 |
| `{"id":8,"cmd":"program.run","name":"Bisque","wait":true,"points":[...],"at":600}` | Store the program and run it from `at` seconds of program time. Without `at`, a running program keeps its current time with the new points swapped in, and otherwise it starts at 0. Rejected with `"start time outside the program"` if that time is at or past the end. Reply: `{"id":8,"ok":true,"updated":false\|true,"program":{...}}` |

`setpoint`, `start` and `program.put` are refused with `"program running; stop it first"` while a program runs. `program.run` is the way to change a running program.

Failures look like `{"id":n,"ok":false,"error":"value out of range"}`.

Other events: `{"evt":"stopped","reason","detail","alarm"}` whenever heating stops (same fields as the status's `stopped`), `{"evt":"tune_done","result":{...}}` or `{"evt":"tune_failed","reason":"..."}` when a step test ends (also when something else stops it), `{"evt":"program_done"}` when a program finishes, and `{"evt":"program_aborted","reason":"..."}` when a reboot mid-program could not resume.

Changes made from the PC show briefly on the Dial (e.g. "SET BY PC"). The controller never depends on the PC: unplugging or closing the page changes nothing on the device.
